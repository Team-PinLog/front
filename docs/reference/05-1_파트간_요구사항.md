# PinLog 파트 간 요구사항

이 문서는 AI·Backend 파트의 설계가 성립하기 위해 **다른 파트(Front, Infra)가 수행해야 하는 요구사항**을 모읍니다. 각 요구사항의 근거는 공용 계약 [AI 설계](05_AI_설계.md)와 정책 문서에 있으며, 여기서는 파트별로 필요한 항목만 정리합니다.

Front·Infra 레포는 이 저장소에서 직접 관리하지 않으므로, 해당 파트는 이 문서를 요구사항 명세로 참조합니다.

## 1. Front 요구사항

### 1.1 Context 수정 시 식별자 변경 (필수)

Context는 불변 엔티티입니다. 수정은 내부적으로 **기존 Context 삭제 + 새 Context 생성**으로 처리되며, **응답에 새 `contextId`가 반환**됩니다([AI 설계](05_AI_설계.md)의 Context 불변성).

Front는 다음을 지켜야 합니다.

- 수정 응답의 **새 `contextId`를 반영**합니다.
- 구 `contextId`로 재조회하지 않습니다.
- 구 `contextId`를 로컬 캐시 키로 계속 사용하지 않습니다.
- URL이나 선택 상태가 Context id를 포함한다면 새 id로 교체합니다.
- Optimistic Update 시 새 id가 오기 전 구 id를 영구 확정하지 않습니다.
- **`createdAt`은 최초 작성 시각으로 보존됩니다.** 수정으로 새 Context가 생성되어도 응답 `createdAt`은 구 Context의 최초 작성 시각을 승계합니다(`origin_created_at`). `contexts` 목록은 `createdAt` 오름차순(오래된순)이 기본이며, 수정해도 목록 위치가 바뀌지 않습니다.

사용자에게는 "수정"으로 보이지만 데이터 관점에서는 새 맥락입니다.

### 1.2 AI 미완료 상태 처리 (필수)

AI 분석은 저장 이후 비동기로 진행되므로, Keyword가 아직 없는 상태가 정상입니다.

- Keyword **빈 배열은 정상 응답**입니다. 로딩 실패나 오류로 처리하지 않습니다.
- Context 생성·수정 직후 Keyword가 잠시 비어 있을 수 있으며, 잠시 후 표시됩니다.
- 수정 재분석 중에는 해당 Context가 자연어 검색·Keyword 응답에서 일시적으로 제외될 수 있습니다.
- **AI 실패가 기본 기능을 막지 않습니다.** Place·Record·Collection은 Keyword 없이도 정상 표시합니다.

### 1.3 Feed 이벤트 전송 (필수)

Feed 추천 결과에 대한 이벤트 중 **`CLICK`·`SAVE`는 Front가 전송**합니다([API 명세](08_API_명세.md) 10.2의 `POST /feed/events`).

- **이벤트는 배열로 묶어 보냅니다.** 이벤트마다 요청을 보내지 않습니다. 배열 크기 상한은 100개입니다(1.5).
- `requestId`는 **배열 바깥의 별도 필드**입니다. 추천 목록 응답에서 받은 값을 그대로 돌려보냅니다. 개별 이벤트 항목 안에 다시 넣지 않습니다.
- 개별 이벤트 항목에는 `event`·`collectionId`·`placeId`·`position`을 담고, `position`도 목록 응답에서 받은 값을 그대로 돌려보냅니다.
- `IMPRESSION`은 Feed 응답 생성 시 서버가 직접 기록하므로 Front가 전송하지 않습니다. 보내면 `400`입니다.
- 저장 구조와 집계 방식은 back 파트의 Feed 문서를 따릅니다([AI 설계](05_AI_설계.md) 17장).

### 1.4 Keyword 공개 등급 표시 (확인 필요)

Keyword는 `PUBLIC` / `PRIVATE_ONLY` / `BLOCKED` 세 등급을 가집니다([익명 SNS 공개정책](04_익명SNS_공개정책.md)).

- 타인 화면에는 `PUBLIC`만 노출됩니다(서버가 필터).
- 본인 화면에는 `PUBLIC`과 `PRIVATE_ONLY`가 제공됩니다.
- **확인 필요**: 본인 화면에서 `PRIVATE_ONLY`를 시각적으로 구분해 표시할지 여부는 제품 결정이 필요합니다.

### 1.5 요청 입력 크기 상한 (필수)

서버가 요청 입력에 방어 상한을 둡니다. 초과 요청은 `400 INVALID_INPUT`이며 `error.fieldErrors`에 위반 필드가 담깁니다.

| 대상 | 상한 | 적용 엔드포인트 |
|---|---|---|
| Context 본문 | **500자** | `POST /records`(`contextBody`) · `POST /records/{recordId}/contexts`(`body`) · `PATCH /records/{recordId}/contexts/{contextId}`(`body`) |
| `recordIds` 배열 | **100개** | `POST /collections` · `POST /collections/{collectionId}/records` |
| `events` 배열 | **100개** | `POST /feed/events` |

Front는 다음을 지켜야 합니다.

- **Context 입력 필드에 `maxlength=500`을 겁니다.** 서버만 막으면 사용자가 긴 글을 다 쓴 뒤에 거절당합니다. 저장 이유 메모는 한 번에 쓰는 성격이라 그 시점에 본문을 잃으면 체감이 나쁩니다. 남은 글자 수를 표시하는 편이 좋습니다.
- **`recordIds`가 100개를 넘으면 나눠 호출합니다.** Record 추가는 멱등이므로([API 명세](08_API_명세.md) §7.5 — 이미 담긴 Record는 건너뛰고 나머지를 담습니다) 나눠 호출해도 중복이 문제되지 않습니다.
- **Feed 이벤트도 100개 단위로 끊어 보냅니다.** 같은 `requestId`의 이벤트가 100개를 넘으면 나눠 호출합니다.
- 서버 400은 방어선으로 남으므로, 받았을 때 `error.fieldErrors`로 어떤 필드가 위반인지 표시할 수 있습니다.

값의 근거는 [데이터 모델](06_데이터모델_및_무결성.md) §8에 있습니다.

### 1.6 Collection 표지 생성 플로우 (필수)

Collection 표지는 이미지 서비스가 생성하고 core는 URL만 저장합니다([API 명세](08_API_명세.md) 7.7). 화풍 선택이 UI 단계이므로 **플로우 오케스트레이션은 Front 담당**입니다. 이미지 서비스 호출 계약은 front#99 연동 가이드를 따릅니다.

Front는 다음을 지켜야 합니다.

- **Collection 생성을 표지 완성에 묶지 않습니다.** 먼저 `POST /collections`로 생성하고, 표지가 확정된 뒤 `PATCH /collections/{collectionId}`의 `coverImageUrl`로 저장합니다.
- `PATCH`에는 상태 폴링에서 `final.status: "done"`으로 확인한 `final.url`만 보냅니다. 서버는 `/image/files/*.webp` 패턴 외의 값을 400으로 거절합니다.
- `coverImageUrl: null`은 표지가 없는 정상 상태입니다. 기본 표지로 폴백하고, 오류로 처리하지 않습니다.
- 사용자가 화풍 선택 전에 이탈해 표지 없는 Collection이 남는 것은 정상입니다. 이후 표지를 등록·교체할 진입점을 제공합니다.
- 폴링 timer는 컴포넌트 unmount 시 정리합니다.
- `WORKER_TOKEN`을 브라우저 코드·환경변수에 넣지 않고, `/image/jobs/*`를 호출하지 않습니다(front#99).

## 2. Infra 요구사항

### 2.1 pgvector 확장 (필수, 블로킹)

AI 벡터 검색은 pgvector 확장에 의존합니다. 현재 운영 PostgreSQL 이미지(`postgres:16-alpine`)와 로컬 개발 이미지에는 pgvector가 포함되어 있지 않아, 확장 없이는 AI 파트가 로컬·운영 어디서도 동작하지 않습니다.

- 운영·로컬 PostgreSQL 이미지를 pgvector 포함 이미지(예: `pgvector/pgvector:pg16`)로 교체하거나, initdb 단계에서 확장을 설치합니다.
- `CREATE EXTENSION IF NOT EXISTS vector`가 `ai` 스키마 대상 마이그레이션 전에 수행되어야 합니다.

### 2.2 `ai` 전용 DB 계정 분리 (필수)

계약상 **FastAPI(AI 워커)는 `core.*`에 접근하지 않으며 DB 권한이 `ai` 스키마로 한정**됩니다([AI 설계](05_AI_설계.md) 접근 금지 경계). 현재 자격증명이 단일 계정(`postgres-credentials`)이라 이 경계가 문서상 약속일 뿐 강제되지 않습니다.

- `ai` 스키마 전용 DB role을 만들고 `GRANT`로 권한을 `ai` 스키마에 한정합니다.
- FastAPI는 이 전용 계정으로 접속하고, `core.*`에 대한 권한을 부여하지 않습니다.
- 네트워크 정책만으로는 스키마 경계를 강제할 수 없으므로 DB 권한 레벨에서 처리합니다.

### 2.3 LLM·Embedding API Key (필수)

Keyword 판정과 임베딩 생성은 외부 LLM·Embedding API를 호출합니다.

- API Key를 SealedSecret으로 관리합니다.
- FastAPI 배포에 주입합니다.

### 2.4 내부 API 노출 차단 (필수)

`/internal/v1/*`는 Spring–FastAPI 내부 통신 전용이며 Client에 노출되면 안 됩니다([AI 설계](05_AI_설계.md) API 보안).

- FastAPI 서비스는 공용 마이크로서비스 차트를 쓰더라도 **`ingress.enabled: false`**로 등록합니다(차트 기본값이 `true`이므로 명시적으로 꺼야 함).
- 서비스 간 인증을 적용합니다.

### 2.5 Embedding Profile 단일 주입 (필수)

Embedding Profile은 Spring과 FastAPI에 각각 하드코딩하지 않고 **배포 설정의 단일 원본에서 주입**합니다([AI 설계](05_AI_설계.md) 모델과 Profile).

- 공통 ConfigMap 등으로 Profile 문자열을 제공하고, Spring·FastAPI가 같은 키를 읽습니다.

### 2.6 서비스 등록 (필수)

- `apps/prod/*`에 back·ai 서비스를 등록합니다. 현재 등록된 서비스가 없습니다.
- AI 서비스는 위 2.4에 따라 ingress를 비활성화합니다.

## 3. 이미지 서비스 요구사항 (INFRA)

Collection 표지가 `core.collection.cover_image_url`에서 이미지 서비스(`Team-PinLog/image`) 파일(`/image/files/*.webp`)을 URL로 참조하면서 생기는 요구사항입니다([API 명세](08_API_명세.md) 7.7).

### 3.1 파일 보존 — 확인 완료 (2026-08-05)

core가 저장하는 것은 URL뿐이므로 **파일이 지워지면 표지가 깨진 링크가 됩니다.** 배포 구성과 서비스 코드를 확인한 결과 참조가 유지되는 것으로 확인했습니다.

- 파일 경로 `/data/files`(`FILES_DIR`)가 PVC(`local-path-retain`, 1Gi)로 마운트되어 파드 재시작·재배포에도 남습니다(`infra/apps/prod/image/values.yaml`).
- 서비스 코드에 파일 삭제 경로가 없습니다. `STALE_JOB_SECONDS`는 잡 회수용이며 파일 정리와 무관합니다.

따라서 표지 계약(API 명세 7.7)은 확정입니다. 다만 남은 두 가지는 이미지 서비스가 관리합니다.

- **정리 배치를 새로 도입한다면 먼저 알려야 합니다.** 선택된 최종본이 지워지면 저장된 표지가 깨집니다. 선택되지 않은 후보 5장은 core가 참조하지 않으므로 자유롭게 정리해도 됩니다.
- 볼륨이 1Gi이고 정리가 없으므로 언젠가 찹니다. 용량 관리는 이미지 서비스 몫입니다.

### 3.2 생성 요청 인증·남용 방지 (확인 필요)

front#99 가이드의 호출 예제에는 인증 헤더가 없습니다. `POST /image/api/covers`는 GPU 비용이 발생하는 작업이므로 확인이 필요합니다.

- 비로그인 사용자의 생성 요청을 허용할 것인지.
- 허용한다면 rate limit 등 남용 방지가 있는지.

| 2.2 `ai` DB 계정 | Infra | 경계 강제 |
| 2.4 내부 API 차단 | Infra | 보안 |
| 2.5 Profile 주입 | Infra + Back + AI | 3자 접점 |
| 1.1 식별자 변경 | Front | 구현 정합성 |

| 1.3 Feed 이벤트 | Front | Feed 동작 |
| 1.4 등급 표시 | Front | 제품 결정 |
