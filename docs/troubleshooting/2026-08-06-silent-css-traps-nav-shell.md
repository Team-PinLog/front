# 조용히 잘못되는 CSS 셋 — safe-area·:focus-within·Tailwind가 주석을 읽는다

- 날짜: 2026-08-06
- 관련 이슈키: S15P11A705-330

## 배경

네비게이션을 sm 하단 탭바 / md 이상 좌측 사이드바로 재구성하며 만난 문제들이다. 셋 다 공통점이 있다 — **타입 에러도 콘솔 경고도 없이 조용히 잘못된다.** 화면을 직접 보거나 빌드 산출물을 열어봐야 드러난다.

---

## 1. `viewport-fit=cover`가 없으면 `env(safe-area-inset-*)`는 **항상 0**이다

### 증상

하단 고정 탭바에 `pb-[env(safe-area-inset-bottom)]`을 주고 iOS에서 확인하면 홈 인디케이터에 탭바가 그대로 가린다. CSS는 정상으로 보이고 클래스도 생성돼 있다.

### 원인

`index.html`의 viewport meta에 `viewport-fit=cover`가 없으면 iOS Safari는 safe-area 인셋을 **0으로 보고한다.** `env()` 자체가 실패하는 게 아니라 값이 0이라 아무 효과가 없다 — 그래서 CSS만 봐서는 원인이 안 보인다.

### 해결

```html
<meta name="viewport" content="width=device-width, initial-scale=1.0, viewport-fit=cover" />
```

**부작용을 같이 처리해야 한다.** `viewport-fit=cover`는 세로 인셋만이 아니라 **가로 인셋(노치)** 도 활성화한다. 폰 가로(예: 932×430)는 이 프로젝트 기준 tier가 `mdlg`라 좌측 사이드바가 뜨는데, `left-0`이면 노치에 가린다. `pl-[env(safe-area-inset-left)]`를 함께 넣었다.

### 재발 방지

safe-area를 쓰기로 했으면 **meta 태그부터 확인한다.** 그리고 이 값은 jsdom·데스크톱 브라우저에서 검증되지 않는다 — 실기기/시뮬레이터 확인이 필수다.

**설계 팁**: safe-area 인셋을 JS 상수로 복제하지 마라. 기기마다 값이 달라 맞출 방법이 없다. 이번에는 탭바 래퍼가 인셋을 padding으로 갖고, 그 래퍼를 `ResizeObserver`로 재서 세로 예산에 넘겼다 — **인셋이 border-box 높이에 포함돼 자동으로 반영된다.**

## 2. `:focus-within`은 클릭 뒤에도 풀리지 않는다

### 증상

md~lg 사이드바를 "평소엔 72px 아이콘 레일, 호버하면 240px로 펼침"으로 만들었다. 호버는 잘 되는데, **메뉴를 클릭해 페이지를 옮기고 마우스를 떼면 사이드바가 펼쳐진 채 그대로 있었다.**

### 원인

키보드 사용자를 위해 `hover:w-60`과 함께 `focus-within:w-60`을 걸었는데, **클릭한 `<Link>`에 포커스가 남는다.** 마우스를 치워도 `:focus-within`이 계속 참이라 펼침이 유지된다.

### 해결

```
hover:w-60 has-[:focus-visible]:w-60
```

`:focus-visible`은 브라우저가 **키보드 조작에만** 적용한다. 클릭 후에는 걸리지 않고, 탭 이동으로 들어온 경우에는 그대로 펼쳐진다. 자식의 포커스를 부모에서 보려면 `:has()`가 필요하다.

`:has()` 미지원 구형 브라우저에서는 호버 전용으로 자연스럽게 후퇴하고, 그때도 접힌 상태의 `<Link> title`·설정 버튼 `aria-label`이 남아 접근성 이름은 유지된다.

### 재발 방지

**"호버로 여는 UI"에 `:focus-within`을 쓰지 않는다.** 클릭 가능한 요소가 안에 있으면 거의 항상 이 문제가 난다. `:has(:focus-visible)`을 쓴다.

## 3. Tailwind는 **주석 속 문자열도** 클래스로 읽는다

### 증상

빌드 산출물을 확인하다 이런 규칙을 발견했다.

```css
.pb-\[calc\(5rem\+…\)\] {
  padding-bottom: calc(5rem + …);
}
```

`…`가 들어간 CSS가 실제로 생성돼 있었다. 소스에는 그런 클래스를 쓴 곳이 없다.

### 원인

`appChrome.ts`의 **JSDoc 주석**에 이렇게 적어 뒀다.

```ts
/**
 * ... AppLayout <main>의 pb-[calc(5rem+…)]와 짝이다.
 */
```

Tailwind는 소스를 **원시 텍스트로 스캔**한다. JS/TS 문법을 이해하지 않으므로 주석인지 코드인지 구분하지 않는다.

### 해결

주석에서 대괄호 리터럴을 뺐다.

```ts
* ... AppLayout <main>의 하단 padding(5rem + 인셋)과 짝이다.
```

### 이것은 [Tailwind 동적 클래스 함정](2026-08-06-collection-spread-redesign-lessons.md)의 **반대 방향**이다

같은 문서 3-1이 "문자열을 조작해 만든 클래스는 스캔되지 않아 조용히 무효가 된다"를 다룬다. 뿌리는 하나다 — **Tailwind는 텍스트만 본다.**

| 방향                          | 결과                                         |
| ----------------------------- | -------------------------------------------- |
| 코드에서 문자열로 조립        | 스캔 안 됨 → 스타일이 **없다**(거짓 음성)    |
| 주석에 클래스처럼 생긴 문자열 | 스캔됨 → 쓰레기 규칙이 **생긴다**(거짓 양성) |

### 재발 방지

주석에서 클래스를 언급할 때 **대괄호 arbitrary value를 그대로 쓰지 않는다.** 값이 중요하면 서술로 풀어 쓴다(`pb-[calc(5rem+…)]` → `하단 padding(5rem + 인셋)`).

이 프로젝트는 Tailwind 리터럴과 JS 상수를 짝지어 두는 곳이 많아(`shelfCabinetLayout.ts`·`appChrome.ts`) 주석에 클래스명을 적을 일이 잦다. `md:pl-[4.5rem]`처럼 **실제로 쓰는** 클래스면 무해하지만, 축약·변형해서 적으면 없는 규칙이 생긴다.

> 참고: 이번에 발견한 것 말고 `.text-\[…em\]`이 하나 더 있었다. 316에서 온 기존 것이라 이번 범위 밖으로 뒀다.

## 공통 교훈

셋 다 **테스트로 잡히지 않는다.** typecheck·lint·단위 테스트를 모두 통과한 상태에서 조용히 틀려 있었다.

이번에는 `npm run build` 후 생성된 CSS를 직접 열어 확인하는 단계를 넣어 2·3을 잡았다.

```bash
npm run build
grep -oE "[^{},]*safe-area-inset-bottom[^{}]*\{[^}]*\}" dist/assets/*.css
grep -oE "[^{},]*focus-visible[^{}]*\{[^}]*\}" dist/assets/*.css
```

**arbitrary value(대괄호 클래스)를 새로 쓸 때는 생성된 CSS를 확인한다.** 리터럴 오타는 "클래스가 조용히 사라지는" 방식으로 깨지기 때문에 화면만 봐서는 원인을 찾기 어렵다.
