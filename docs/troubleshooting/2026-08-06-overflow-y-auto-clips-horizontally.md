# `overflow-y-auto`가 가로도 클리핑한다 — 선반 판 그림자가 잘리던 원인

- 날짜: 2026-08-06
- 관련 이슈키: Jira 작업

## 증상

탐색(`/feed`) 화면에서 선반 판(`ShelfPlank`)의 낙하 그림자가 **판 좌우 끝에서 수직으로 뚝 잘려** 보였다. 판이 상자에 끼워진 것처럼 보이는 증상이다.

맨 아래 선반만이 아니라 **모든 행**에서 나타났다. 315에서 "맨 아래 선반 판의 그림자가 잘린다"는 같은 계열의 증상을 한 번 고쳤는데(`FEED_ROWS_PADDING_BOTTOM_PX = 24` 추가), 그때는 세로 방향만 해결됐고 좌우는 그대로 남아 있었다.

재현: `npm run dev` → `/feed` → 선반 판의 좌·우 끝을 본다. 폭과 무관하게 전 구간에서 재현된다.

## 원인

행 스크롤 박스의 클래스가 `flex flex-col overflow-y-auto`였다.

`overflow-y`만 `auto`로 지정하고 `overflow-x`를 지정하지 않으면, **CSS는 `overflow-x`를 `visible`로 두지 않고 자동으로 `auto`로 승격한다.** CSS Overflow 명세상 `overflow-x`/`overflow-y` 중 한 축이 `visible`이고 다른 축이 `visible`이 아니면, `visible` 쪽이 `auto`로 계산된다. 즉 "세로만 스크롤" 의도로 쓴 클래스가 실제로는 **가로도 클리핑**한다.

선반 판은 스크롤 박스 폭을 꽉 채우고 있었고, 그 그림자는

```
box-shadow: 0 10px 16px rgba(4,33,66,.13)
```

로 x offset이 0, blur가 16px이다. blur는 도형 경계를 기준으로 안팎으로 절반씩 퍼지므로 판의 좌·우 끝에서 **정확히 8px씩** 바깥으로 나간다. 그 8px이 스크롤 박스 경계에서 잘려 나갔다.

세로 방향(아래로 offset 10 + blur 절반 8 = 18px)은 315가 넣어 둔 아래쪽 padding 24px이 이미 받아주고 있어서 문제가 드러나지 않았다 — **가로만 여백이 없었다.**

## 해결

두 단계로 나눠 고쳤다. 첫 번째로 잘림을 없애고, 그 뒤에 드러난 별개의 문제를 다시 고쳤다.

### 1) 잘림 제거 — 여백 확보 + 가로 예산 반영

`FEED_PLANK_SHADOW_BLEED_PX = 8`을 `shelfCabinetLayout.ts`에 신설하고, 이 폭을 스크롤 박스의 좌우 padding으로 넣었다(`FEED_ROWS_PADDING_X_PX`).

⚠️ **여백을 확보하는 것만으로는 부족하다.** 같은 폭을 가로 예산에서 함께 움직여야 한다.

- `getFeedGridAreaWidthPx`에서 **차감** — 빼지 않으면 확보한 여백이 그대로 카드 폭을 침범해 선반 덩어리가 페이지 컨테이너를 넘고 가로 스크롤바가 생긴다.
- `getFeedShelfWidthPx`에 **가산** — 더하지 않으면 선반 판이 그만큼 좁아진다.

세로 여백(24px)과 달리 여유분을 얹지 않았다 — 폰트 지표 같은 브라우저 편차가 없는 결정적 값이다.

### 2) 잘림을 없애니 드러난 별개의 문제 — 끝단 단면

클리핑을 없앤 뒤에는 그림자가 판 끝에서 **세로선처럼 뚝 끝나는 것**이 보였다. 이건 클리핑과 다른 문제다 — `box-shadow`는 요소의 사각형을 그대로 복제해 흐리는 것이라 끝단에 항상 단면이 남고, **여백을 아무리 줘도 해결되지 않는다.**

낙하 그림자를 `box-shadow`에서 **별도 레이어로 분리**하고 좌우 페이드아웃 마스크를 걸었다(`Shelf.tsx`의 `ShelfPlank`).

- 세로 프로파일은 기존 `0 10px 16px`이 만들던 띠를 그대로 재현한다(판 바로 아래에서 시작해 24px 아래에서 사라지고, 가장 진한 지점이 판에서 조금 떨어져 있다).
- 좌우 페이드는 판 폭의 **양 끝 5%씩**. px이 아니라 %로 잡은 이유는 판 폭이 구간마다 크게 다르기 때문이다(sm 약 300px ~ xl 약 1450px) — 고정 px이면 좁은 화면에서는 판 전체가 흐려지고 넓은 화면에서는 끝이 여전히 끊겨 보인다. 처음 10%로 잡았다가 "그림자가 선반보다 짧아 보인다"는 피드백으로 5%로 줄였다(온전한 그림자 구간 80% → 90%).
- 그림자 레이어를 판보다 좌우로 정확히 `FEED_PLANK_SHADOW_BLEED_PX`만큼 넓게 잡아, 1)에서 확보한 padding·예산 계약이 그대로 유효하다.

## 재발 방지

- **`overflow-y-auto`(또는 `overflow-x-auto`) 한 축만 지정한 스크롤 박스 안에서, 자식이 박스 경계 밖으로 그리는 것(그림자·아웃라인·hover 리프트·회전)은 반대 축에서도 잘린다.** 한 축만 쓴 스크롤 박스에 그림자 있는 자식이 들어가면 반대 축 여백을 함께 확인한다.
- 이 프로젝트에서 그런 여백을 넣을 때는 **반드시 레이아웃 예산에 반영한다.** `shelfCabinetLayout.ts`가 카드 크기를 역산하므로, 예산에 없는 여백은 계산상으로만 맞고 실제로는 스크롤바를 만든다. 세로는 `getFeedRowsContentBudgetPx`, 가로는 `getFeedGridAreaWidthPx`가 차감 지점이다.
- **`box-shadow`로는 끝단 단면을 없앨 수 없다.** 그림자가 어느 방향으로든 자연스럽게 사라져야 하면 처음부터 별도 레이어 + 마스크로 만든다.
- 회귀 테스트를 `shelfCabinetLayout.test.ts`에 넣었다. 기존 "선반 덩어리가 컨테이너 안에 들어간다" 테스트는 `getFeedGridAreaWidthPx`의 식을 그대로 되짚는 형태라 **그림자 여백을 빼먹은 상태에서도 통과했다** — 독립적으로 계산한 `getPageContainerWidthPx`와 직접 비교하도록 바꿨다. 검증식이 대상 함수의 식을 재사용하면 그 함수가 무엇을 빠뜨리든 항상 통과한다는 점에 주의한다.
