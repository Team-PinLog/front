# 운영 백엔드 /dev/auth/login 노출 여부 확인

- 날짜: 2026-08-06
- 관련 이슈키: S15P11A705-342

## 증상

#114 리뷰에서 발견된 항목. `PlaceRecordPreviewPage`의 "테스트 세션 발급" 버튼이 인증 없이 아래를 호출한다.

```ts
await fetch('/api/core/v1/dev/auth/login', { method: 'GET', credentials: 'include' });
```

프론트 라우트(`/dev/place-record`)에는 접근 가드가 없어, 운영 백엔드가 이 엔드포인트를 실제로 노출하고 있다면 URL만 아는 누구나 로그인 없이 세션을 발급받을 수 있는 경로가 열린 셈이다. 프론트 코드만으로는 백엔드가 이 경로를 살려 뒀는지 알 수 없어 실측이 필요했다.

## 원인

확인 전에는 알 수 없음 — 백엔드 프로파일(dev/prod) 분리 여부에 달려 있다.

## 해결

운영 도메인에 실측 요청.

```
$ curl -s https://pin-log.com/api/core/v1/dev/auth/login
{"success":false,"error":{"code":"UNAUTHORIZED","message":"인증이 필요합니다.","fieldErrors":[],"traceId":"..."}}
→ HTTP 401
```

이 응답 형태(`UNAUTHORIZED`, HTTP 401)는 존재하지 않거나 보호된 다른 경로에 인증 없이 접근했을 때와 동일하다. 즉 운영 환경에서는 이 경로가 "인증 없이 세션을 내주는" 방식으로 동작하지 않는다 — 프론트가 우려했던 로그인 우회 경로는 운영에서 실제로 열려 있지 않음(확인됨).

다만 이 결과만으로 "엔드포인트가 아예 존재하지 않는다"까지는 단정할 수 없다(추정) — Spring Security의 기본 인증 진입점이 매핑되지 않은 경로도 보호된 경로와 동일하게 401로 막을 수 있어서, 이 실측만으로는 두 경우를 구분할 수 없다.

## 재발 방지

- 프론트: 라우트 자체를 `import.meta.env.DEV`로 감싸 프로덕션 번들에서 제외(S15P11A705-342, `docs/conventions.md` 7장에 규칙 추가).
- 백엔드: dev 프로파일 전용 컨트롤러가 prod 프로파일 빌드/설정에 포함되지 않는지는 백엔드 팀 확인이 필요하다. 이번 실측상 운영에서 열려 있지 않음이 확인됐으므로 별도 이슈 승격은 하지 않는다.
