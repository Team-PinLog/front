# 컬렉션 펼친 화면 재설계에서 반복된 함정들 (레인 시야·죽은 소비자·Tailwind·지도)

- 날짜: 2026-08-06
- 관련 이슈키: Jira 작업

여러 세션이 worktree를 나눠(L1 상세 / L2 표지 / L3 책장) 동시에 작업하는 중에 Jira 작업를
진행하며 겪은 문제를 모았다. 개별 버그보다 **반복된 패턴**이 남길 가치가 있어 한 문서로 묶는다.

---

## 1. 이미 있는 컴포넌트를 못 찾고 새로 만들 뻔했다

### 증상

"Collection 상세 오른쪽에 작성자의 다른 컬렉션 책장을 세워 달라"는 요구를 받고,
`src/features/collections/components/CollectionShelfPanel.tsx`를 **새로 만들었다**.
조율 세션이 바로 잡았다:

> 우측 책장 패널은 새로 만들지 마라 — 이미 있다.
> `src/features/feed/components/ShelfExploreSection.tsx`를 재사용해라.
> `useShelfExploreQuery(collectionId)`로 "이 작성자의 다른 컬렉션"을 이미 조회하고 Follow/Unfollow도 한다.
> `CollectionDetailView`에서 `!ownedByMe`일 때 이미 렌더 중이다(지금은 책 아래 리스트 형태).

실제로 그 컴포넌트는 **내가 편집 중이던 파일 안에서 이미 렌더되고 있었다.**
새로 만든 파일은 삭제하고 기존 컴포넌트를 리스킨하는 것으로 되돌렸다.

### 원인

worktree 규칙(`CLAUDE.local.md`)이 "내 파일 목록 밖은 건드리지 않는다"로 되어 있고,
그 목록에 `features/feed/*`가 없었다. 그래서 **"내 파일이 아니다" → "내 관심사가 아니다"로
미끄러졌다.** 목록은 *수정 권한*의 경계인데 *탐색 범위*의 경계로 취급한 것이다.

`CollectionDetailView.tsx`에 `<ShelfExploreSection collectionId={collectionId} />`가 그대로 있었고
import 문도 파일 상단에 있었다 — 못 볼 수 없는 위치였는데도, "새 패널을 만든다"는 과제 프레임이
잡히자 기존 렌더 트리를 훑지 않았다.

### 해결

- 새로 만든 `CollectionShelfPanel.tsx` 삭제.
- `ShelfExploreSection.tsx`를 그 자리에서 리스킨(하단 카드 목록 → Library 1열 캐비닛)하고
  위치만 책 옆으로 옮겼다. 데이터 경로(`useShelfExploreQuery`)·Follow 로직·이동 경로는 그대로 뒀다.
- 조율 세션이 이 파일을 이번 티켓에서 L1 소유로 확정했다.

조율 세션이 덧붙인 근거가 중요하다:

> ⚠️ 데이터 경로를 새로 만들지 마라. 이 경로가 `collectionId`를 진입점으로 쓰는 것이
> `privacy-rules.md`의 "`member.id` 미사용" 요구를 만족시키는 근거다.

즉 중복 구현은 코드 중복 문제로 끝나지 않고 **개인정보 규칙의 근거를 잃는 문제**가 될 수 있었다.

### 재발 방지

- **새 컴포넌트를 만들기 전에, 그 기능이 이미 렌더되고 있는지 호출부에서 먼저 확인한다.**
  최소한 `grep -rn "<도메인 키워드>" src`와 지금 편집 중인 파일의 import 목록을 훑는다.
- **"내 파일 목록"은 쓰기 권한의 경계이지 읽기·탐색의 경계가 아니다.** 탐색은 항상 `src` 전체를 본다.
- 레인 밖 파일을 고쳐야 하면 **멈추고 조율 세션에 보고**한다(기존 규칙). 이번처럼 "고쳐야 하는데
  내 파일이 아니라서 새로 만든다"는 우회는 규칙 위반보다 나쁜 결과를 만든다.

## 2. 소비자를 지웠더니 생산자 4곳이 허공에 대고 호출하게 됐다

### 증상

오버레이 셸을 재작성하면서 `CollectionDetailPage`의
`consumeCollectionOverlayIntent()` 호출을 걷어냈다. 그 결과:

- `consumeCollectionOverlayIntent()` — **소비자 0곳** (죽은 코드)
- `markCollectionOverlayIntent()` — **호출부 4곳이 그대로 살아 있음**
  - `src/features/feed/components/FeedList.tsx:244`
  - `src/features/feed/components/ShelfExploreSection.tsx:205`
  - `src/features/follows/components/FollowedShelfCard.tsx:198`
  - `src/features/collections/components/MyShelfList.tsx:149`

네 곳이 매번 플래그를 세우지만 아무도 읽지 않는다. 타입 에러도 lint 경고도 나지 않는다 —
export된 함수라 "미사용"으로 잡히지 않고, 호출부는 정상적으로 존재하는 함수를 부르고 있다.

### 원인

`collectionOverlayIntent`는 207에서 "방금 클릭해서 진입"과 "새로고침으로 재진입"을 구분하려고
만든 인메모리 플래그다. 332에서 딤·카드 패널을 없애 **두 경우의 화면이 같아지면서** 그 구분
자체가 불필요해졌고, 소비 지점만 지웠다.

생산자·소비자가 파일로 분리돼 있고(`lib/collectionOverlayIntent.ts`), 생산자 호출부가 전부
**내 파일 목록 밖**(feed·follows·collections의 다른 컴포넌트)이라 시야에 들어오지 않았다.
1번과 같은 뿌리다.

### 해결

이번 티켓에서는 **생산자 호출부를 지우지 않았다** — 네 파일 모두 다른 레인이 수정 중이라
건드릴 수 없다. 대신 PR 본문의 "다른 티켓의 전제가 바뀐 것"에 정리 대상으로 명시했다.

부작용 자체는 무해하다(추정): 플래그를 세우기만 하고 읽지 않으므로 동작에 영향이 없고,
메모리도 boolean 하나다. 다만 **읽는 쪽이 없는 채로 계속 세워지는 상태**라, 나중에 누군가
이 플래그를 다시 읽으면 "항상 true"인 값을 만나게 된다 — 그때가 실제 버그가 되는 시점이다.

### 재발 방지

- **소비자를 지울 때 생산자도 함께 본다.** 모듈 스코프 플래그·이벤트·전역 상태처럼 호출 관계가
  타입으로 이어지지 않는 것은 컴파일러가 알려주지 않는다.
  지우기 전에 `grep -rn "<모듈명>" src`로 **양쪽 방향**을 모두 센다.
- 생산자를 당장 지울 수 없으면(레인 분할 등) **죽은 소비자를 남기지 말고 후속 티켓으로 명시**한다.
  "지웠다"와 "지울 예정이다"를 코드가 아니라 PR·티켓에 남긴다.

## 3. 디자인 6라운드에서 실제로 헤맨 것들

시안 반영 후 디자인 피드백을 여러 차례 받으며 반복해 걸린 함정들. 공통점은 **에러가 나지 않고
조용히 어긋난다**는 것이다.

### 3-1. Tailwind 클래스를 문자열로 조립하면 조용히 사라진다

책과 책장이 같은 높이를 써야 해서 상수 하나를 재활용했다:

```ts
const BOOK_HEIGHT_CLASS = 'md:h-[600px] xl:h-[720px]';
// 책장은 lg부터 나란히 서므로 브레이크포인트만 바꿔 쓰려 했다
className={BOOK_HEIGHT_CLASS.replaceAll('md:', 'lg:')}
```

Tailwind는 **소스에 리터럴로 존재하는 클래스만 스캔**하므로 `lg:h-[600px]`은 CSS가 아예 생성되지
않는다. 에러도 경고도 없이 높이만 안 먹는다. 리터럴 상수 두 개로 나눠 해결했다.

- **재발 방지**: 클래스 문자열에 `replace`·템플릿 연산을 쓰지 않는다. 조건부는 완성된 리터럴 중
  하나를 고르는 형태(`cond ? 'md:h-[600px]' : 'md:h-[420px]'`)로만 쓴다.
  (이미 `shelfCabinetLayout.ts` 상단에 같은 취지의 주석이 있었다 — `grid-cols-{N}`을 동적으로 만들 수
  없어 인라인 style을 쓴 사례. 같은 함정이 다른 속성으로 반복됐다.)

### 3-2. 지도 핀이 0×0으로 찌그러져 아예 보이지 않았다

홈 지도와 같은 핀 SVG를 컬렉션 지도에 쓰려고 `CustomOverlay` + `<img>`로 옮겼는데 **핀이 하나도
보이지 않았다.** 원인은 Tailwind preflight의 `img { max-width: 100%; height: auto }` —
`CustomOverlay`가 content를 감싸는 래퍼 div의 폭이 0이라 `max-width: 100%`가 0으로 계산된다.
`width`/`height` **속성**만으로는 부족하고 `style.maxWidth = 'none'` + 인라인 px 크기가 필요하다.

가장 뼈아픈 점: `RecordMapView.createRecordMarkerElement`에 **이 함정과 해결책이 이미 주석으로
적혀 있었다.** 코드는 참고했는데 그 주석을 함께 옮기지 않아 같은 버그를 다시 만들었다.

- **재발 방지**: 기존 구현을 참고해 옮길 때 **경고성 주석(⚠️·"~하면 안 된다")은 코드보다 먼저
  옮긴다.** 그 주석이 존재한다는 것 자체가 "이미 한 번 당했다"는 뜻이다.

### 3-3. "번쩍임"의 원인을 두 번 잘못 짚었다

"책장에서 새 책을 열면 번쩍인다"는 피드백에 두 번 헛다리를 짚었다.

1. 1차 추정 — 로딩 시 한 줄 텍스트만 반환해 레이아웃이 붕괴한다 → 스켈레톤 도입. **여전히 번쩍임.**
2. 2차 추정 — 스켈레톤에 인덱스 레일 폭(80px) 자리가 없어 가로로 밀린다 → 자리표시자 추가.
   **일부만 개선.**
3. 실제 원인은 **사용자가 지목**했다: 목차 장과 record 장의 높이가 조금 다른데, 오버레이 셸이
   콘텐츠를 `items-center`(세로 중앙)로 두고 있어 **그 작은 차이가 화면 전체의 상하 이동으로
   증폭**되고 있었다.

두 번의 수정도 실제 결함이었지만(둘 다 유지했다), 지배적 원인은 아니었다.

- **재발 방지**: 시각적 증상은 "무엇이 변하는가"만 보지 말고 **"무엇이 그 변화를 증폭하는가"**를
  함께 본다. 세로 중앙 정렬·`justify-center`·`transform` 기준점은 작은 차이를 전체 이동으로 바꾼다.
- 두 번 추정이 빗나가면 **더 고치기 전에 증상 위치를 사용자에게 묻는다.** 3라운드에서 물었더니
  한 번에 특정됐다. 추정으로 두 번 고치는 동안 실제 결함 세 개가 코드에 섞여 들어갔다.

### 3-4. 겹침 좌표를 두 곳에서 따로 계산해 글자가 잘렸다

인덱스 레일 탭을 "책 오른쪽 가장자리에 물린" 모양으로 만들면서 레일에 `-ml-3`(12px)을 줬는데,
책 표지가 페이지보다 8px 크다는 것(`-inset-2`)을 계산에 넣지 않았다. 총 20px이 가려지는데 탭의
왼쪽 패딩은 16px이라 **장소명 첫 글자가 표지 뒤로 잘려 들어갔다.**

- **재발 방지**: 두 요소를 의도적으로 겹칠 때는 **겹침 총량을 한 곳에 적어두고** 패딩을 그보다 크게
  잡는다. 이번에는 음수 마진을 없애고 표지 턱 8px만 겹치게 한 뒤 `pl-5`(20px)로 정리했고,
  그 계산 근거를 `CollectionIndexRail`의 JSDoc에 남겼다.

### 3-5. `fitBounds`가 바꾼 확대 레벨이 되돌아오지 않던 잠복 버그

record 장의 확대 레벨을 6 → 3으로 당기면서 발견했다. 기존 코드는 지도 **생성 시에만** 레벨을
정하고 이후에는 `setCenter`만 했는데, 목차 장의 `fitBounds`가 레벨을 바꿔 놓기 때문에
**목차를 한 번 거친 뒤부터는 record 장이 전체 bounds 레벨 그대로** 남았다.

레벨 6(축척 500m)일 때는 차이가 눈에 띄지 않아 드러나지 않았고, 3(축척 50m)으로 당기자 바로
보였다. `setLevel`을 매 전환마다 명시적으로 호출하도록 고쳤다.

- **재발 방지**: 지도처럼 **명령형 API로 상태를 바꾸는 객체**는 "이 화면에서 원하는 상태"를 매번
  전부 설정한다. "생성 시 한 번 설정 + 이후 일부만 갱신"은 다른 경로가 그 상태를 바꿔 놓으면
  깨진다.

## → conventions.md 반영 필요

아래 세 가지는 이번 건에 한정되지 않는 규칙이라 `docs/conventions.md` 반영 후보다.
**직접 수정하지 않았다 — 사용자·조율 세션 확인 후 반영한다.**

1. **Tailwind 클래스는 리터럴로만 쓴다.** 문자열 조작(`replace`·연결)으로 만든 클래스는 스캔되지
   않아 조용히 무효가 된다. 조건부는 완성된 리터럴 중 하나를 고르는 형태로 쓴다.
2. **새 컴포넌트를 만들기 전에 기존 구현을 먼저 찾는다.** worktree의 "내 파일 목록"은 쓰기 권한의
   경계이지 탐색 범위의 경계가 아니다. 레인 밖 파일을 고쳐야 하면 우회하지 말고 보고한다.
3. **모듈 스코프 플래그·전역 상태의 소비자를 지울 때 생산자도 함께 확인한다.** 타입으로 이어지지
   않아 컴파일러가 알려주지 않는다. 당장 지울 수 없으면 후속 정리 대상으로 명시한다.
